# 下一步执行清单：云端评估、本地前端、L0 优化

> 目标：按“先保证数据可信，再做对比评估，再推进演示落地，再规划下一轮优化”顺序执行，避免空转。

---

## 1) 云端：核查预处理数据 + 用新指标评估 L0 与基线

### 1.1 先做数据真实性核查（必须）

- 核查对象：
  - `data/processed/hydro/*.npz`
  - `data/processed/stats/hydro_zscore.npz`
  - `data/processed/stats/hydro_preprocess_meta.json`
- 核查项：
  - `X/y` 形状、样本数、通道顺序是否与 `config/hydro_*.yaml` 一致。
  - `hydro_zscore.npz` 中 `mean/std/features` 是否存在且与当前训练使用的特征顺序一致。
  - 随机抽样对比：反标准化后的样本统计是否与原始 nc 量级一致（避免“看起来全正常但量纲漂移”）。

### 1.2 预处理数据若“有误”的处理原则

- 触发条件（满足其一即可判定“有误”）：
  - 特征顺序错位或通道统计明显不合理（例如某通道方差异常接近 0）。
  - 反标准化后与原始 nc 的同区域/同时间量级严重不一致。
  - 明显的数据截断/缺文件导致样本分布失真且无法解释。
- 处理策略：
  - 优先回退到原始数据重跑预处理（保持同一 `config/data.yaml` 口径，记录差异）。
  - 若仅统计量异常，先修复预处理统计写出逻辑再重生 `processed`。
  - 所有修复均以新输出目录或完整日志区分，避免覆盖旧结果不可追溯。

### 1.3 使用“其他指标”对 L0 与基线做对比（在数据可信后）

- 对比对象：
  - 基线：`outputs/hydro_l2/best.pt`（或云端备份 **`AutoDL/outputs/hydro/`**；通过 `--baseline-ckpt` 传入）
  - 创新：`outputs/hydro_l0/best.pt`
- 推荐新增指标（至少做前 3 项）：
  - 分通道 MAE/RMSE（temp/sal/u/v 分开，不只看平均）。
  - Skill（相对 persistence/朴素基线）：`1 - MSE_model / MSE_ref`。
  - Pearson 相关系数（逐通道或区域均值序列）。
  - 物理量纲误差（反标准化后 RMSE/MAE，单位可解释）。
- 输出要求：
  - 生成可入材料表的 `csv/md`。
  - 在结论中单列“L0 相对基线是否稳定改进（是/否）”。

### 1.4 云端验收标准

- 已形成“数据可信/不可信”结论及证据（文件路径+日志）。
- 已给出 L0 vs 基线的新增指标对比表。
- 若数据不可信，已完成回退原始数据重跑并复评。

### 1.5 已落地：自动化核查 + 扩展指标对比（仓库内）

实现位置：

- `scripts/hydro_cloud_assessment.py`：子命令 **`audit`**（预处理与统计量核查）、**`compare`**（同一 `val`/`test` npz 上对两个 checkpoint 算扩展指标）。
- `src/hydro/extended_metrics.py`：逐通道 **MAE、RMSE（归一化空间）**、**Skill（相对持久性基线：输入末时刻铺满预报窗）**、**Pearson**，以及可选 **物理尺度 RMSE**（`RMSE(norm)*std[channel]`，需传入 `hydro_zscore.npz`）。

最小命令（在云或本机、`F:/创赛` 为仓库根的前提下）：

```bash
# 1) 数据核查 — 选择与当前 disk 上 npz 一致的 hydro yaml（否则会列 issues）
python scripts/hydro_cloud_assessment.py audit \
  --hydro-config config/hydro_hycom_l0.yaml \
  --data-config config/data.yaml \
  --out-json outputs/cloud/hydro_preprocess_audit.json

# 若本地仅存「烟测」合成样本（通道/网格与 hycom 配置不一致），请改用对齐的 yaml，例如：
# python scripts/hydro_cloud_assessment.py audit --hydro-config config/hydro_synthetic.yaml --data-config config/data.yaml

# 2) L0 vs 基线 — 仓库内默认 L2 为基线路径；也可用 --baseline-ckpt 指向云端备份（如 AutoDL 目录）
python scripts/hydro_cloud_assessment.py compare --split val \
  --baseline-config config/hydro_hycom_l2.yaml \
  --baseline-ckpt outputs/hydro_l2/best.pt \
  --experiment-config config/hydro_hycom_l0.yaml \
  --experiment-ckpt outputs/hydro_l0/best.pt \
  --stats-npz data/processed/stats/hydro_zscore.npz \
  --out-table-md submission/tables/hydro_l0_vs_baseline_val.md \
  --out-csv submission/tables/hydro_l0_vs_baseline_val.csv \
  --out-summary-json outputs/cloud/hydro_compare_val_summary.json
```

约定：

- `compare` 会检查两条 yaml 中的 `val_*`/`test_*` npz **路径一致**；若不一致需加 **`--force`**（否则退出），避免误判。
- 持久性 Skill 公式：`1 - mean((pred − y)^2) / mean((persist − y)^2)`，`persist` 为输入序列**最后一帧**在时间维重复到预报长度。

## 3) L0 下一轮优化方案池（先列方案，再按成本执行）

### 3.1 低成本优先（建议先做）

- 损失权重微调：
  - `loss.eos_constraint.weight` 下调（如 `0.1 -> 0.03/0.05`）。
  - `mae_weight` 下调或设 `0` 做对照，观察 temp 与 u/v 的权衡。
- AttnRes 复杂度调整：
  - `attn_res.num_blocks: 8 -> 4/6`
  - `attn_res.reduction` 适度增大，减轻过拟合和显存压力。
- 训练稳定性：
  - 学习率小范围网格（`1e-4`, `7e-5`, `5e-5`）。
  - 固定 seed 做可复现实验，不同时改太多参数。

### 3.2 中成本方案

- 通道加权损失（重点 u/v）：
  - 在训练中提升 u/v 权重，直接针对主误差来源。
- 分阶段训练：
  - 先 L2 收敛，再迁移到 L0 微调，比较是否更稳。

### 3.3 高成本方案（评估后决定）

- 预处理策略迭代（分通道归一化、鲁棒缩放等）并全量重跑。
- 新增更强物理约束（需确保反标准化与公式口径严格一致）。

### 3.4 方案筛选规则

- 任何新方案若未稳定优于基线（至少 val/test 两侧均改善），不进入主交付。
- 若改进幅度很小但复杂度显著增加，保留为“探索结果”，主交付回落稳定版本。

## 4) 完成先前规划的台风知识库

### 4.1 范围边界（沿用既有决策）

- 仅做**自动化、可复现**部分，不引入人工标注/人工清洗依赖。
- 本阶段目标是“知识库可用 + 可追溯”，不强求一次到位的事件级最优检索指标。

### 4.2 本阶段完成项（必须落地）

- 数据侧：
  - 固化台风公开数据来源与下载脚本（如 CMA/IBTrACS；以可获取源为准）。
  - 统一原始数据落盘目录与版本标识（日期、来源、字段说明）。
- 处理侧：
  - 生成台风事件索引（`json/csv`）：事件 ID、时间范围、中心位置、强度级别等。
  - 生成与 anomaly 可对接的检索键（按时间窗与空间范围映射）。
- 服务侧（可简化）：
  - 提供最小可用查询接口/脚本：输入时间窗与区域，返回候选事件列表与摘要。
  - 结果可导出，便于材料和演示引用。

### 4.3 验收标准

- 知识库构建可一键或最小步骤复现（命令可写入 README/docs）。
- 同一输入查询得到稳定一致输出（非随机漂移）。
- 可给出至少 2 个案例：与异常检测结果联动展示“检索到的台风事件”。

  - 一键入口：`scripts/run_typhoon_kb.sh`、`scripts/run_typhoon_kb.ps1`。
- 新增模块：
  - `src/anomaly/typhoon_kb.py`：台风事件聚合、检索键生成、确定性查询打分。
