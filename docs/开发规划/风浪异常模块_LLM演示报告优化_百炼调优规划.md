# 风浪异常模块 LLM 演示报告优化规划（百炼调优优先）

> 范围：在**不调改赛题核心回归/检测算法**的前提下，优化**最终对外叙述层**；技术路线以**阿里云百炼平台 + 调优大模型**为起点，向下推导数据、评测、接口与前端展示。

---

## 1. 问题与现状

### 1.1 体验问题

- **专业数据裸露**：上游（视频/时序）推理后，`run_detect` 与规则模板 `render_report` 会输出残差、z 值、DTW、台风候选表等**面向研发**的字段，演示观众难以在数秒内建立「发生了什么、有多严重、该怎么办」的心智模型。
- **无台风时的叙述空洞**：知识库未命中时，报告常停留于「未检索到候选台风事件」类表述，**缺少对「无历史台风可比」场景的合理解释与后续动作**，易造成「系统什么也没做」的观感。

参考实现位置（便于后续改造挂载点）：`src/anomaly/report.py`（规则模板四段）、`app/pages/result.py`（联动与表格展示）。

### 1.2 约束

- **事实锚定**：风浪是否异常、等级、时空窗、候选台风列表等仍以**现有算法输出**为准；LLM **不得捏造**具体台风编号、时间或观测数值；仅能作**白话解释、影响推断（带不确定性表述）、类比与行动建议**。
- **离线可演示**：API 不可用时应**降级**到当前规则模板报告，不出现空白页。
- **合规**：不在客户端硬编码密钥；日志避免输出完整密钥与用户原始视频路径（若涉及隐私场景）。

## 2. 目标（最终输出形态）

在前序模块已完成、并得到结构化检测结果（不论是否判定为异常）后，风浪**最终输出端**统一经由大模型生成一篇**固定四段结构**的中文报告：

| 段落 | 作用 | 对无台风场景的最低要求 |
|------|------|------------------------|
| **是否异常描述** | 用非专业读者可懂的话总结判定结论与置信度语感 | 明确「当前窗口内模型/规则如何判定」，避免堆砌数字 |
| **影响判断** | 结合异常等级与时空范围，说明**可能影响**与**不确定边界** | 说明「无台风命中不代表无风险」等，避免绝对化 |
| **历史类比** | 若有 Top-K 台风：概括相似点；若无：说明**为何不可比**、可转向哪些公开资料或业务预案 | **禁止**编造事件；可写「知识库内无足够重叠的台风个例」并建议查阅路径 |
| **建议动作** | 监测、复核、升级、与业务方协同等可执行短句 | 给**默认建议**（如保持监测、关注后续窗口），与异常等级联动 |

输出建议采用 **JSON Schema 约束**（便于前端渲染与审计），例如字段：`summary_anomaly`、`impact`、`historical_analogy`、`actions`（`actions` 可为字符串数组）。具体键名在调优数据阶段与模型约定死。

## 3. 规划起点：百炼平台「调优大模型」

以下顺序为**推荐执行顺序**：先定**教学数据与评测**，再选基座与微调方式，最后接 API 与产品。

### 3.1 选基座与微调类型

- **基座**：选用百炼上**支持微调**且**中文海洋/气象叙述**表现稳定的对话模型（具体型号以控制台当前列表为准，建议选**通义系**中档以上上下文窗口，便于塞入完整 `detect_output` JSON）。
- **微调类型（优先）**  
  - **有监督微调（SFT）**：主路径。用「算法侧结构化输入 → 四段报告」成对样本 teaching。  
  - **可选：DPO/偏好对齐**：在 SFT 之后，用「同一输入下：更简洁演示版 vs 冗长版」做偏好，减少废话与数字堆砌。  
- **是否必须微调**：若时间极紧，可先**仅 API + 强系统提示词**做 MVP；但本方案以**调优**为交付目标，以保证口吻稳定、无台风场景叙述一致、且少越权编造。

### 3.2 训练数据设计（核心）

#### 3.2.1 输入（模型可见上下文）

统一打包为**一个 JSON**（与线上一致），建议字段子集包括：

- `anomaly_result`：`anomaly_level`、`anomaly_index`、`wind_residual` / `wind_z`、`wave_residual` / `wave_z`、`threshold_rule`、`assessment_note` 等（与 `run_detect` 对齐）。
- `typhoon_link.query`：时间窗与 bbox。
- `typhoon_link.candidates`：0～K 条（含 `event_id`、`name`、时间、`score`、`dtw_distance` 等）；**无候选时为空列表**。
- `meta`（可选）：`module_version`、`demo_scenario`（如 `答辩演示-有台风` / `答辩演示-无台风`）。

**注意**：训练与推理时应对敏感原始路径脱敏；视频级信息若仅用于旁白，可提炼为「已检测涡旋时间轴摘要」等二级文本，避免把整段 timeline 原样塞入（按 token 预算裁剪）。

#### 3.2.2 输出（监督信号）

每条样本对应**严格 JSON**（或固定分隔标题的 Markdown，二选一；**推荐 JSON** 利于解析）：

- 四段正文 +（可选）`disclaimer`：「本段为辅助说明，业务判定以命题方与现场数据为准」。

#### 3.2.3 样本分层（保证「无台风」不比「有台风」少）

建议比例（可随数据量调整）：

- **A 类**：高/中异常 + 有 1～3 个高质量候选（训练模型**如何引用**台风信息而不泄露未给出字段）。  
- **B 类**：低/无异常 + 无候选（训练**温和结论 + 仍给建议**）。  
- **C 类**：高异常 + 无候选（训练**不强行关联台风**、强调其他致因可能性与监测）。  
- **D 类**（鲁棒性）：字段缺失或 `assessment_note` 含「降级/无曲线」类信息，模型应显式说明**数据局限**。

数量级建议：答辩级至少 **200～500 条**有效 SFT 条；其中 B+C 合计 **≥40%**。

#### 3.2.4 数据合成与标注流程

1. **半自动**：用当前 `render_report` + `run_detect` 真实 JSON 批量生成**草稿**四段，人工改写成演示口吻。  
2. **人工审核清单**：是否胡编台风名/时间；是否出现未在 `candidates` 中出现的 `event_id`；数字是否与输入一致或明确标为「约」。  
3. **冻结测试集**：按 A/B/C/D 分层留出 **15%～20%** 不参与训练，用于后文评测。

### 3.3 百炼侧操作要点（实施时以官方文档为准）

- 创建**调优任务** → 上传 **JSONL**（每行一条多轮对话或单轮 instruction-output）。  
- 配置学习率、epoch、最大长度；观察**过拟合**（对训练事件背稿）时加大 D 类或加正则/早停。  
- 部署为**可调用的模型端点**（记录 `model` 名或 endpoint id），与生产环境**非生产密钥**隔离。

### 3.4 评测（调优验收）

| 维度 | 方法 |
|------|------|
| **格式** | JSON 可解析率 100%；必填四键非空率 |
| **忠实度** | 抽检：输出中的台风名/ID 必须 ⊆ `candidates`；无候选时不得出现具体台风编号 |
| **演示可读性** | 人工打分 1～5（非专业人员阅读）；平均分 ≥4 |
| **无台风模板** | C 类子集：**禁止**仅以「未检索到」收尾，必须包含影响边界说明 + ≥2 条建议 |
| **延迟** | P95 在百炼链路可接受范围内（答辩前设定上限，例如 8～15 s 内可配合 loading 文案） |

## 4. 推理与工程集成（接在数据与微调之后）

### 4.1 调用链路（逻辑顺序）

1. 上游产出 `detect_output`（与线上一致）。  
2. **后处理**：将 `detect_output` 裁剪为固定 schema（省略大字段）；可选附加 `human_hint`（演示员一句旁白）。  
3. **百炼 Inference**：system prompt 固定写法（海洋监测助理角色 + 严守输入事实 + JSON -only）。  
4. **校验**：JSON parse + 规则检查（台风名白名单来自 candidates）。不通过则**重试一次**或降级规则报告。  
5. **前端**：默认展示「**报告卡片**（四段）」；技术详情折叠保留原表格/JSON。

### 4.2 配置与安全

- 环境变量：`BAILIAN_API_KEY`、`BAILIAN_MODEL_ID`（示例名，以实际为准）。  
- **不在仓库**提交密钥；`app/config` 中仅保留占位与说明。  
- 实现阶段若引入官方 Python SDK，需按仓库规范写入 **`requirements.txt`** 并注明版本。

### 4.3 降级策略

- LLM 超时 / 配额 / 校验失败 → 调用现有 `render_report`。  
- 可在规则报告中增一行：**「以下为规则模板自动生成（大模型不可用）」。**

## 8. 方案评估与修订要点（外部评审回填）

> 本节为对方案可行性与优先级的独立评估结论，用于指导排期；**不改变**第 1～7 节的技术设计框架。

### 8.1 总体判断

- **方向成立**：叙述层与算法层解耦、事实锚定、JSON 结构、无台风场景与降级策略，与「赛题可复现 + 演示要人话」的双重目标一致。  
- **主要风险不在「使用大模型」**，而在**答辩环境网络**、**SFT 标注成本**，以及是否把「微调」误当作必须的第一步。

### 8.2 方案中已较强的部分

- 问题定义（专业数据裸露、无台风叙述空洞）与现有代码挂载点一致。  
- 工程链路（裁剪 → 调用 → 校验 → 降级）可审计、可落地。  
- 无台风（B/C 类）与忠实度（台风信息 ⊆ `candidates`）写进数据与评测，避免常见方案遗漏。  
- 明确不改动回归评测口径，材料与答辩好解释。

### 8.3 风险与代价（实施前对齐预期）

| 项 | 说明 |
|----|------|
| **SFT 性价比** | 固定四段 + 固定 JSON 往往可用「基座 + 强 system prompt + 校验」先达到答辩可用；SFT 价值在口吻统一、无台风段落不偷懒、少胡编，但需 **200～500 条量级**的标注与审核成本。 |
| **过拟合与分布偏移** | 低质量或套话化 SFT 可能过拟合；需保持与线上一致的 `detect_output` schema，并保留 §3.4 评测与冻结测试集。 |
| **答辩环境** | 公网/配额/延迟不稳定时，仅「失败才降级」仍可能观感差；建议准备 **预生成报告**（对少数演示快照）或与规则模板并列的**手动切换**。 |
| **产品层** | 同一份检测结果应 **按 hash 防抖**、避免视频链高频重复调 LLM；可改为用户点击「生成解读报告」再请求。 |
| **合规** | 「影响判断」「建议动作」需与 `disclaimer` 及命题方免责用语一致（见 §7）。 |

### 8.4 路径选型（辅助决策）

| 路径 | 适用 |
|------|------|
| 加厚规则模板（无 LLM） | 极短工期、禁止联网。 |
| **基座 + Prompt + JSON + 校验 + 降级**（推荐**必做首段**） | 尽快闭环演示、控制成本。 |
| 百炼 SFT（本文主路径） | Prompt 路径仍不稳，或材料强调「领域微调」时加重投入。 |
| 预生成答辩剧本 | 现场网络不可靠时的**保险杠**（3～5 个 `detect_output` 快照离线定稿）。 |

### 8.5 修订后的推荐实施顺序（相对 §5 表）

1. **优先**：JSON schema 定稿 + **`llm_report` 工程壳**（调用、校验、降级）+ **基座 API + 强提示词**跑通闭环（对应原 P0 中 schema 与部分 P2）。  
2. **并行**：准备 **80～120 条**高质量种子样本与审核表；若 Prompt 路径已满足 §3.4，可将全量 SFT 缩减为 **B/C/D 子集**专项。  
3. **再决策**：是否投入百炼全量 SFT（原 P1）与 DPO（原 P3）。  
4. **答辩前**：预生成 + 三档开关（实时 API / 预生成 / 纯规则）与延迟、配额压测。

## 9. 首次部署烟测复盘与正式 SFT 数据

> 本节基于 **`scripts/test_dashscope_model.py`** 对接已部署快照（控制台 **部署代号** 示例：`qwen3-14b-b8880c898590`；以你当前线为准）的烟测：**`no_typhoon` / `with_typhoon` / `degrade`** 三场景。**仅供叙述层迭代**，不涉及回归评测口径变更。

### 9.1 烟测效果结论（简述）

| 场景 | 主要优点 | 主要问题 |
|------|----------|----------|
| **无候选台风** | 四字段 JSON 齐全，类比段已向「暂无可对齐个案」演进，可读性明显高于仅提示「未检索到」。 | 个别表述仍可加强「不等价于海区无风险 / 不排除其它成因」；避免语气过硬如「无法进行类比」。 |
| **有候选** | **仅引用 candidates 内 ID/名称**，忠实度较好。 | 类比段易泛化成「历史上类似台风常……」等与单条候选弱绑定措辞；易出现 **无依据百分比概率**；避免出现 **「该系统」指代台风** 的病句。 |
| **降级（缺曲线）** | 能复述 `assessment_note` 与 `wave_z: null` 带来的局限。 | **summary 过短**；**candidates 非空却写「知识库未收录/依据不足」** 自相矛盾；偶发 **JSON 在 `actions` 处截断**。 |

**其它**：在输入**未给单位字段**时，模型可能**自行补 m/s、m** —— 属轻度「脑补量纲」。线上应在 **JSON 中显式带单位** 或在 system 中禁止补单位（本仓库正式数据已按后者约束 system）。

### 9.2 据此对「正式微调数据」的约束（已固化进生成脚本）

- **System**：单一来源见 `src/anomaly/llm_sft_report_prompt.py`（与 `scripts/test_dashscope_model.py` 共用）。明确：无单位字段时不得自造 m/s、m；**禁止虚构百分比与「通常/往往」式外推**；**candidates 非空时不得写「知识库未收录致因」**；有候选时类比仅复述候选字段与 query 关系；禁止天气过程被误称「该系统」；**level 与 z 不一致**时的综合判定解释；降级时 **summary 至少两句** 且复述 `assessment_note`；**actions 至少 3 条且输出须为完整可解析 JSON**。  
- **Assistant（合成教官）**：`degrade` 场景 impact 首段显式承认弱候选存在并解释证据链被波高降级削弱；`with_typhoon` 的类比段改为「仅列 score / overlap / dtw 等已给字段」，不写统计概率。  
- **分层（约）**：无候选 ≈40%；有候选 ≈38%；降级 ≈12%；边角（level/z 张力）≈10%。  
- **用户 JSON**：仅含 `anomaly_result` + `typhoon_link`（与线上一致），**不含** `meta` 等调试键。

### 9.4 推理侧烟测脚本（与 r2 对齐）

- `scripts/test_dashscope_model.py` 已改为 **import** `src/anomaly/llm_sft_report_prompt.py` 中的 system，与训练数据一致。  
- 默认传入 **`max_tokens=2048`**（可用 `--max-tokens` 或环境变量 `DASHSCOPE_MAX_TOKENS`），减轻 **`actions` 被截断** 的概率。  
- 打印 **`json_check`**：校验 `json.loads` 成功且四键齐全、`actions` 长度 ≥3。
